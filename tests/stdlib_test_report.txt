================================================================
ROOT CAUSE ANALYSIS
================================================================

CRITICAL BUG #1: cmp3/if3 Branch Mapping Mismatch
--------------------------------------------------
The VM's cmp3() returns trit type values (TRUE/MAYBE/FALSE).
The if3 construct maps: TRUE->if-branch, MAYBE->maybe-branch(?), FALSE->else3-branch
But testing shows MAYBE actually goes to else3, not maybe branch.
This breaks ALL stdlib functions that use the pattern:
  if3 cmp3(a, b) { // a > b } maybe { // a == b } else3 { // a < b }
Because when a==b, cmp3 returns MAYBE but if3 routes to else3.

CRITICAL BUG #2: Variable Scoping with "let" in Inner Blocks
-------------------------------------------------------------
"let x = expr" inside for3/if3/try3 blocks creates a NEW local variable
that shadows the outer variable. When the block exits, the outer variable
is unchanged. This pattern is pervasive in stdlib:
  let result = []
  for3 item in lst {
    let result = push(result, item)  // BUG: creates NEW local "result"
  }
  return result  // returns original empty []
The correct pattern should use assignment without "let":
  result = push(result, item)

CRITICAL BUG #3: Trit Type vs Integer Confusion
------------------------------------------------
sign3, not3, and3, or3 return trit arithmetic results (TRUE/MAYBE/FALSE)
but callers expect integer values (1/0/-1). str(TRUE) = "TRUE", not "1".
This makes these functions unusable for integer-expecting code.

BUG #4: format3 while3 loops with cmp3() == -1
-----------------------------------------------
The pattern "while3 cmp3(i, n) == -1" compares a trit to integer -1.
While this works for the == check itself, the while3 loop may not
iterate correctly due to the trit/integer type mixing.
